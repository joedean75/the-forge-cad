# Shared-state audit: what a second API worker breaks

*`SCALE-01` and `SCALE-02`. The list is complete for the state this system keeps
in a process; each row says what happens with two workers, what was done, and
what remains.*

The rule this audit applies: **an in-memory structure is a cache or it is a
bug.** A cache is one whose miss is paid by an authoritative read. Anything else
is a value that exists on one worker and not the other, and the symptom is
always the same shape — it works, then intermittently does not, at a rate the
load balancer sets, and nothing in the logs says why.

## Addressed

| State | With two workers | Now |
| --- | --- | --- |
| **Account indexes** (`accounts._ACCOUNTS`, `_EMAIL_INDEX`, `_APIKEY_INDEX`, `_STRIPE_INDEX`, `_OAUTH_INDEX`) | A signup on worker A is unknown to worker B, so the next request reports invalid credentials for an account that plainly exists | Every lookup falls through to the datastore on a miss and indexes what it finds. Email and Stripe id are filtered in SQL (`persistence.accounts_by_field`); API-key fingerprints and OAuth subjects are nested and scan, which is a cache miss cost paid at most once per key per process. |
| **OAuth state and handoffs** (`oauth._PENDING`, `_HANDOFFS`) | The flow spans two requests. The callback lands wherever the balancer sends it and the PKCE verifier was minted elsewhere, so sign-in fails about half the time with "invalid or expired sign-in attempt" — which reads as a provider fault | Rows in the datastore (`persistence.save_ephemeral` / `take_ephemeral`), with the read and delete in one transaction so single-use survives concurrency. Still server-side, still never sent to the browser. |
| **Optimize and package jobs** (`_OPTIMIZE_JOBS`, `_PACKAGE_JOBS`) | A job submitted to A is a 404 when the poll lands on B, indistinguishable from a job that never existed | `services/jobs`: rows, claimed with a compare-and-set, with a lease so a dead worker's job is requeued rather than left `running` forever. |
| **Generated bytes** (mesh, thumbnail, export LRUs) | A URL the client was told to cache forever 404s on the instance that did not generate it | `services/blobs`, with a filesystem adapter. `FORGE_BLOB_DIR` on a shared volume makes a URL valid everywhere. Unset it stays in memory, which is correct for a single instance. |
| **Document write races** | Two edits both read revision 3, both apply, both report 4 | `document_service.writing(doc_id)` serializes the read-modify-write. **Per process** — see below. |
| **G-code on the document** | Stripped on persist, so a reload lost it even on one worker | An artifact with a content hash, like every other generated file. |

## Not addressed, and what that means

| State | Consequence | Position |
| --- | --- | --- |
| **Rate limits** (`rate_limit._hits`) | Each worker keeps its own buckets, so N workers means N times the configured limit | Accepted and documented. These are flood control, not a quota — quota metering is per account and goes through the datastore. The fix is a shared counter, and it is not worth a Redis dependency for a limit whose purpose is to bound damage rather than to be exact. Set the per-worker limit to `limit / workers` if the total matters. |
| **The document write lock** | Per process. Two workers can each hold "the" lock for one document | This is the real gap in `SCALE-02` and it is why multi-worker stays conditional. The optimistic path is still safe — `expected_revision` is checked against the persisted revision — but two writers that both omit it can still interleave. Closing it needs the revision check to be a conditional UPDATE in SQL, the same shape as `persistence.claim_job`. Sized but not built. |
| **`DOCUMENTS` in-memory cache** | Worker B can hold a document worker A has since written | Bounded by the same rule as the rest: reads that matter go through `get_document`, which loads from the datastore on a miss but **prefers** a held object. Two workers can therefore disagree until a restart. Mitigated by the realtime channel below on a single instance; not solved. |
| **Collaboration WebSockets** (`realtime._ROOMS`) | A room exists per process, so two collaborators connected to different workers never see each other's edits | Needs a pub/sub fan-out (Postgres `LISTEN/NOTIFY` is the dependency-free option here). Until then, collaboration is a single-instance feature and enabling a second worker silently degrades it — which is the worst kind of degradation, so it gates the rollout rather than being shipped alongside it. |
| **Evaluated-solid and B-rep caches** | Each worker builds its own | Correct as is. These are caches of a pure function of the tree, so a miss is slow and never wrong, and the objects (OCC shapes) are not serialisable in any case. |

## The gate

Multi-worker is **conditional, not the definition of done**. Before raising the
worker count:

1. The document write lock is a conditional UPDATE, not a process lock.
2. Collaboration either fans out across processes or is explicitly disabled.
3. `FORGE_BLOB_DIR` points at storage every instance can read.
4. `FORGE_JWT_SECRET` is set — with a per-process fallback key, a session is
   valid or a 401 depending on which worker answers, and `main._check_production_posture`
   already refuses to start in that configuration.
5. The mixed-load run in `benchmarks/load.py` passes against two workers with
   authentication, job polling, artifact fetches and document edits in the mix.

Rows 1 and 2 are open. **Production stays single-worker until they close**, and
that is a supported configuration rather than a temporary state — everything
above works correctly on one instance, and the durability work stands on its own
merits there (a restart no longer loses jobs or generated files).
