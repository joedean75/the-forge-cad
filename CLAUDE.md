# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A browser-based replica of the Forge (The Forge) generative-design workflow. The UI is a presentation-layer mockup, but the backend runs a **real 3D SIMP topology optimizer** and a **from-scratch SDF-based CAD kernel** — those are the parts with real substance, not stubs.

The operation catalog is also intended as the **action space for an LLM agent**, and increasingly as something a model can be fine-tuned against: typed and validated arguments, results that say what changed, verifiers that can score a part, and recorded trajectories. Changes to that surface should keep it machine-checkable — see the note in Architecture.

**Two kernels, and which one runs matters.** The SDF kernel is the original: robust booleans that never fail, and the only thing that can evaluate a voxel density field from the optimizer or an imported mesh. **OpenCascade now runs alongside it** (`cad_kernel/evaluator/brep.py`) and is tried *first*, because it is the one that gives geometry an identity — addressable faces and edges, exact dimensions, and real STEP. `Kernel.evaluate_feature` tries B-rep → native Rust SDF → numpy SDF, and `derived.sampler` records which ran.

`brep_from_feature` returns `None` for anything it cannot represent faithfully, and one such feature disqualifies the **whole tree** — half a body built exactly and half approximated is worse than either. What it declines, and why: `FilletFeature`/`ChamferFeature` are smooth booleans *between bodies*, not edge treatments; `ShellFeature` is `abs(d) - t/2`, which hollows uniformly and cannot open a face; `OptimizeFeature`/`ImportFeature` are cached voxel grids. `LoftFeature` is declined for a different reason worth understanding: `LoftSDF` blends the two profiles' *distance values*, which is not a ruled surface, so an OCC loft would be a genuinely **different shape** — mapping it would silently change what an existing document means depending on whether OCC is installed. The true loft is therefore `RuledLoftFeature` (`add_ruled_loft`), a second feature rather than a swap behind the same name. It is exact enough that a circle-to-circle loft matches the conical-frustum formula to 1e-6 relative and a square-to-square one matches the pyramid frustum, which is how you know the surface is genuinely ruled; `ruled=False` asks `ThruSections` for the smooth variant instead.

Revolve, sweep and sheet metal **are** mapped, each matched to the field semantics rather than to the obvious OCC call: a partial revolve sweeps symmetrically (−angle/2..+angle/2, not 0..angle), and a sweep is built from cylinders and spheres because `SweepSDF` is a union of *capsules* — `BRepOffsetAPI_MakePipe` would give flat ends and mitred joints, a different body at every corner. `SheetMetalFeature` rebuilds `SheetMetalSDF`'s own construction: an annular sector welded to the plate edge plus a leg tangent to its end, extruded across the part. Anything else — a fillet on the corner, say — would be a body `flat_pattern` does not unfold. The two kernels agree to 0.25% across five bend configurations, which is 200³ voxels on a 1.5 mm sheet.

The real versions of the first two are separate features (`ops/exact.py`): `EdgeFilletFeature`, `EdgeChamferFeature`, `FaceShellFeature`, driven by `fillet_edges` / `chamfer_edges` / `shell_faces`, plus `BrepBodyFeature` — an imported STEP/IGES solid carried as deflated OCC BRep, deserialized on every evaluation. These exist **only** on the exact kernel — their SDF builders raise rather than approximate, and `Kernel.evaluate_feature` rebuilds them strictly rather than falling back, so a failure says "OCC could not build a 500 mm fillet on those edges" instead of a generic "needs the exact kernel".

OCP is an **optional** dependency (~143 MB). Without it everything still works through the SDF, but no face or edge is addressable and STEP export is faceted.

## Commands

Backend (run from `backend/`):
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000    # dev server
pytest                                          # all tests
pytest tests/test_cad_kernel.py::test_name      # single test
```

Frontend (run from `frontend/`):
```bash
npm install
npm run dev        # Vite dev server on :5173, proxies /api -> :8000
npm run build      # tsc -b && vite build  (type-check is part of the build)
npm run lint       # oxlint
```

Both at once: `./start.sh` (expects the backend venv to already exist). Or `docker-compose up`.

There is no frontend test suite; `npm run build` is the type-check gate.

**Driving it headlessly** (rollouts, dataset generation): `tests/conftest.py` is the working bootstrap — temp SQLite via `DATABASE_URL`, empty `FORGE_DATA_DIR`, `FORGE_RATE_LIMIT=0`, and `FORGE_AUTH_REQUIRED` left unset so every request is attributed to a shared enterprise dev account. Call `cad_operations.execute` directly to skip HTTP, auth and quota metering entirely. Over HTTP, `POST /api/documents/{id}/op?envelope=1` returns failures as 200 bodies instead of raising.

Two things used to bite at volume and now have a switch: `services/rollout.py`. `with rollout.rollout(resolution=192):` turns metering off and pins resolution, or `FORGE_ROLLOUT=1` (+ `FORGE_ROLLOUT_RESOLUTION`) sets it process-wide. The quota one is obvious — a few hundred thousand edits exhausts even the enterprise allowance and the failure arrives as a 402 mid-rollout. **Pinning matters more**: `capped_resolution` clamps to the account's plan, so the same document evaluates differently for different accounts, which destroys the one property a dataset needs — that a recorded observation can be reproduced. Both are opt-in and scoped to a block; neither touches `can_access`, which is the security boundary rather than a billing counter.

## Architecture

**Two processes, one API contract.** React/Vite frontend talks to a FastAPI backend only through `/api/*`. In dev, Vite proxies `/api` to `:8000` (`frontend/vite.config.ts`). In production, FastAPI mounts the built `frontend/dist` at `/` (see the `StaticFiles` mount at the bottom of `backend/main.py`), so the whole app ships from one URL.

**Shared types are duplicated, not imported.** `shared/types.ts` (consumed by the frontend via relative import `../../../shared/types`) mirrors the Pydantic models in `backend/app/models/schemas.py`. These two must be kept in sync **by hand** — changing a response shape means editing both.

**The frontend is a screen router around one persistent document.** `useNavStore` moves between `signin → library → editor/assembly` (hash-synced). Inside the editor, `useDocumentStore` holds the open `DesignDocument` and the six modes on the load-path spine — Model, Optimize, Analysis, Make, Validate, Machine — each a panel under `frontend/src/features/*`. `useAuthStore` and `useAssemblyStore` cover sessions and assemblies. All server calls funnel through the typed `api` object in `frontend/src/api/client.ts` — add new endpoints there, not with ad-hoc `fetch`.

**Topology-addressing operations reach the UI through the catalog, not through bespoke endpoints.** `api.listFaces` / `listEdges` / `filletEdges` / `chamferEdges` / `shellFaces` / `checkReferences` / `getSpec` / `setSpec` / `verifyAgainstSpec` / `analyse` are typed wrappers over `runOperation`, so the UI makes the same call an agent does. Three things there are load-bearing:

- **The face picker is a list, not a 3D overlay.** `Kernel.from_mesh` produces one `Face` with `surface=None`, so the display mesh carries no face ids: a click on it locates a *point*, never an entity. A nearest-entity guess would be right most of the time, which is the worst possible accuracy for a selection. `TopologyPicker` lists entities with the measurements that tell them apart and `DocumentViewport.TopologyMarkers` marks the *selected* ones — marking every listed one is either clutter or invisible, both of which were tried.
- **`DfmReport.process` is a display label** (`LPBF`, `MILLING`), not the id that was requested, so nothing may compare it to a `DfmProcess`. The store keeps `dfmProcess` — what was asked for — and every "is this report current?" and additive-versus-not label keys off that.
- **`simulate` is called as an operation, not via `POST /simulate`.** That endpoint's `SimulationResult` drops `solver` and `estimate_only`, so a closed-form fallback arrives looking exactly like a solve. `AnalysisReport` in `shared/types.ts` is the full shape.
- **The sketch canvas reports the solver's *status*, not `converged`.** `features/sketch/SketchCanvas.tsx` shows a chip with `well_constrained` / `under_constrained` / `over_constrained` / `conflicting` and the remaining dof, and `under_constrained` deliberately gets no warning colour — it is the normal state of a sketch someone is drawing, and colouring the normal state red trains people to ignore the indicator. Dimensions are drawn *on* the sketch (`SketchDimensions.tsx`) with click-to-edit figures rather than listed in the sidebar: a row saying `distance 60.0mm` cannot tell you *which* 60 mm. `sketchEdit.ts` holds trim/extend/offset/mirror as pure functions over the entity lists — they edit the drawing, not the constraint system, and a constraint naming an entity a trim replaced is dropped rather than left to fail in the solver.
- **The part behind the sketch is shaded, and its projected mask needs its winding normalised.** `PartBackdrop` offers `shaded` (an orthographic view down the plane normal), `section` (only the material the plane cuts, filled by scanline parity over the section edges), `outline` and `off`. **Depth carries most of the shading, not the light**: looking straight down a plane's normal every parallel face has the same Lambert term, so a pocket floor and the plate around it come out the same grey — mapping distance to brightness is what makes a boss read as raised. The silhouette, holes included, comes from eroding the mask and subtracting, not from guessing at grazing triangles. The mask itself is the trap: filling every triangle into one path and calling `fill(path, 'nonzero')` is wrong for a *closed* body, because the near and far faces project with opposite winding and sum to zero — that is why the backdrop used to be invisible for every real part, with only the section line showing. Flipping each triangle to a positive projected area first makes nonzero a union.
- **The canvas zooms, and everything that is not geometry scales with it.** The view is `{cx, cy, span}` in millimetres; `k = span / 260` multiplies every stroke width, point radius, dimension offset and font size, so they hold their size on screen while the part zooms. `SketchGrid` picks its spacing off the span on a 1-2-5 ladder and labels the majors. The rubber-band preview is drawn to the *snapped landing point*, not the raw pointer — a preview that disagrees with the click is worse than no preview.

`shared/types.ts` once declared `DesignSpec` **twice** — the generative-optimization spec and the requirements spec — and TypeScript merges same-named interfaces silently rather than erroring, leaving one type that demanded every field of both. The requirements one is `PartSpec`, which is what `DesignDocument.spec` actually holds. Check before adding a name.

The older linear 7-step flow (`requirements → generative → topology → …`), its `useAppStore`, and the candidate-based backend it talked to (`routers/cad|export|optimize|simulate|manufacturing|text_to_cad|design|assembly`, `services/mesh_generator|assembly_generator|design_intent`) were **removed** — every capability now lives on the document API. Don't reintroduce a `Candidate`; the durable unit is a `DesignDocument`.

**Backend layering:** `routers/` (HTTP surface) → `services/` (orchestration/business logic) → `cad_kernel/` (pure geometry engine). Keep geometry math in `cad_kernel`; keep request handling thin.

**The operation catalog is an action space, not just an API.** It is meant to be driven by a model, so it is built to be *machine-checkable* rather than merely self-describing: every operation publishes strict JSON Schema (`GET /api/operations`, or `GET /api/operations/tools` in function-calling form), arguments are validated before a handler runs, failures carry a stable code, and every result reports what changed. The pieces are `services/op_schema.py` (schema + validation), `op_errors.py` (typed failures), `observation.py` (the compact state an agent sees, and the delta between two of them), `geometry_check.py` (is it a valid solid), `trajectories.py` (recording what was done), and `decompiler.py` (recovering an op sequence from a tree). If you are adding to the surface, the test to apply is: could a model tell from the response alone whether it succeeded, why not, and what changed?

**Topological naming** (`cad_kernel/core/naming.py`) is what makes selection survive a rebuild. OCC's `TopoDS_Face` identity does not — change a dimension and the "same" face is a different object in a different exploration order. Entities are named by *what they are*: kind, size, and position **normalised to the body's bounding box**. That last part is load-bearing. Stretch a plate from 80 to 120 mm and its corner edges move 20 mm absolute, which no sane tolerance accepts; normalised they have not moved at all, so a fillet placed on them stays put. A reference that cannot be matched is reported unresolvable rather than snapped to whatever was nearest. `services/datum.py`'s symbolic `{feature_id, face}` scheme is the SDF-side equivalent and still applies when the body is not exact.

**Descriptors cannot survive an edit that re-topologises, so references are also followed** (`cad_kernel/core/history.py`). Cut a slot across a filleted face and the face becomes two faces, each with a new size and a new normalised position: measuring finds one of them, or neither, and both answers are wrong — the reference now names *both*. Every face and edge therefore also carries a **tag**, an identity rather than a measurement, minted as `{feature_id}:{kind}:{index}` by the feature that created it and propagated through OCC's `Modified`/`Generated`/`IsDeleted` maps on every rebuild. `naming.resolve_references` tries the tag first and falls back to descriptors, which stay as the answer for a `BrepBodyFeature` read from STEP (no construction history by definition) and for references stored before tags existed. Four details are load-bearing:

- **A tag's index is scoped to the feature that made the entity**, not to the finished body. `BRepPrimAPI_MakeBox` visits its six faces in the same order whatever the dimensions, so a resize renumbers nothing; global exploration order would renumber on every edit.
- **Absent history is the normal case, not an error.** A primitive has no input to have a history *from*, and `BRepFilletAPI` says nothing about the edges it did not touch. A stage that reports nothing about a sub-shape is read as "it came through unchanged", and if it did not, the tag just fails to appear and descriptor matching takes over.
- **Only the booleans are believed about deletion.** `BRepFilletAPI_MakeFillet.IsDeleted` returns `True` for box edges that are plainly still there, so `history.advance` takes `trust_deleted` rather than assuming it. Reported `deleted` short-circuits the descriptor fallback on purpose: given a face destroyed by an upstream edit, measuring will happily find something 0.5 mm away and move the fillet onto it, which is the silent mis-selection the whole scheme exists to prevent.
- **A successor has to be the same kind.** A fillet `Generated`s a *face* from an edge; that face is the new fillet surface, not the edge renamed.

The verdicts are collected during the build — the only time the intermediate bodies exist — and cached on `document_service.ExactBody` alongside the shape and the tag map. `check_references` reads them back (`matched` / `split` / `deleted` / `unresolved`), and `document_service.reference_verdicts` still returns them when the build *failed*, which is exactly when "the four edges you picked are gone" is the only useful thing to say. `execute` warns when an edit leaves a body that still builds but reaches fewer edges than it was given.

**The CAD kernel** (`backend/app/cad_kernel/`) is self-contained: a `FeatureTree` of primitives (`ops/primitives.py`) and booleans (`ops/booleans.py`) is evaluated as a signed distance field (`evaluator/sdf.py`), meshed via marching cubes (`geom/meshing.py`), and exported to STL/STEP/DXF (`io/`). `kernel.py` is the public facade.

**Adding a feature type** takes two edits, both data: define the class in `ops/` under `@register_feature`, and add one line to `_SDF_BUILDERS` in `evaluator/sdf.py`. `tests/test_registries.py` fails immediately if you do only one. There is no import list or `isinstance` chain to keep in step any more.

**Adding an operation** takes one edit: decorate the handler with `@operation(name, kind, description, params)` in `services/cad_operations.py`. The catalog, the REST surface, the MCP server and the UI all read from that registry. Mark an argument the handler cannot work without as `{"required": True}` — `services/op_schema.py` turns the block into strict JSON Schema and validates against it *before* the handler runs, so a malformed call is refused rather than half-applying an edit. Fetch an argument with `op_errors.require(args, "name")`, never `args["name"]`: the bracket form raises `KeyError`, which used to surface to the caller as `404 Not found: 'sketch'`.

**The catalog addresses two kinds of thing, and each operation says which.** `@operation(..., subject="assembly")` (default `"document"`) puts a handler in `services/assembly_operations.py`, and `execute` routes through a `_Subject` table — how to load the thing, how to observe it, how to diff two observations — rather than through a special case only the copilot would know about. The id an operation is handed therefore names either a part document or an assembly, published in `GET /api/operations` so a caller knows *before* it calls; `POST /api/assemblies/{id}/op` is the other door and each route refuses the other's operations with a pointer instead of a 404 on a perfectly real id. Nine operations were added there and not one of them is new capability: the mate solver, `interference` and `bom` were implemented, routed and tested, and unreachable from the surface every model drives. **Creating** an assembly is deliberately not an operation, for the same reason creating a document is not — both are a `POST` on a collection, and it would be the only operation whose id argument means nothing. `observation.summarize_assembly` says `kind: "assembly"` because an agent driving both gets two differently-shaped states and one that infers which from the presence of a key will eventually infer wrong.

**An assembly has a mass budget, and it is not the BOM's total.** `services/assembly_mass.py` reports all-up weight, centre of gravity and inertia tensor in assembly space — the three numbers an airframe, a drone or a robot is checked against. Mass adds trivially and the BOM already did that; the other two do not. The CG is the mass-weighted mean of each part's **own** centre of mass carried into assembly space by its placement — using the component's bounding-box centre is the tempting shortcut and it is wrong for every bracket. The inertia tensors are rotated (`R I R^T`) *before* the parallel-axis shift; summing them without the rotation is right only when nothing is turned, which is exactly the case mate connectors exist to stop being true. A scaled instance is **excluded and says why**: mass goes as `s^3` and inertia as `s^5`, and density belongs to the material rather than to the instance. Components are ranked by `moment_g_mm` rather than by weight, because a light part on a long arm outvotes a heavy one at the centre — and for a two-body system those moments are equal, which is the cheapest end-to-end check there is.

**`export_urdf` is the payoff of mate connectors.** A URDF link needs a mass, a centre of mass and an inertia tensor; a joint needs two frames and an axis. Before connectors there were no frames to write, so every joint would have been `fixed` and the file would have described a statue. What it refuses to fake is the interesting half: URDF is a **tree**, so a closed loop (a four-bar, a differential) is named as unsupported rather than dropped; URDF has **no cylindrical and no spherical joint**, so those emit `fixed` and say so, because a joint that silently loses a degree of freedom is a robot that behaves differently in simulation than on the bench; and a `revolute` mate emits `continuous`, because URDF's `revolute` requires a `<limit>` and inventing one puts a travel stop in the simulation the machine does not have. One thing was wrong first: **URDF's joint frame *is* the child link frame**, so the origin carries *both* connectors (`F_base . offset . F_moved^-1`) — emitting the base connector alone is correct only when the moved connector sits at the part origin. `<axis>` is in the joint frame, which reduces it to the moved connector's own z column.

**A mate is a relationship between two frames, and the frames live in the parts.** There are two mate schemes and a mate says which by whether it names connectors. The original four — `fasten`, `coincident`, `concentric`, `distance` — read a component's **bounding-box extremes** along one world axis. That places a bolted stack and nothing else, and the limit is structural rather than a missing count: an extreme cannot express a rotation, so every one of those mates leaves the part axis-aligned, and there is nothing to say "this hole, not that one". Adding eight more types to that scheme would have been adding rows to the wrong table.

`MateConnectorFeature` is the table — a named frame (origin, mate axis, in-plane reference) that is an ordinary bodyless feature of the part, alongside `SketchFeature` and `DatumPlaneFeature` in `BODYLESS_TYPES`. `revolute`, `slider`, `cylindrical`, `planar`, `ball` and `parallel` are all one operation — align the two frames — with a different set of degrees of freedom left free, and they are the only way a part gets *rotated* into place here. Five things are load-bearing:

- **The legacy four are unchanged, deliberately.** Assemblies are persisted, and a stack that shifts because the solver grew a second scheme is a wrong answer for every document already saved. `_apply` is untouched; the connector path is a separate branch taken only when both sides name one.
- **Frames are re-read on every resolve, never copied onto the mate.** A connector is a feature of the part, so moving it — or resizing the part around it — has to carry the mate with it. A frame cached at mate time is a stale placement that looks right until somebody edits the part. `assembly_service.connector_frames` does the lookup, which keeps `assembly_mates` a pure function of its arguments.
- **Degrees of freedom are a property of the constraint, not of the placement.** A revolute leaves one rotation free and the solver still has to *pick* a value for it; reporting DOF from what it picked would report zero for everything. The `dof` operation reports 6 minus what each mate's type removes, floored at zero, and says `over_constrained` rather than clamping — two mates can be individually valid and jointly impossible, and the count is the cheapest signal that they are.
- **A connector-only mate with no connectors is refused at the operation**, and so is a connector id that names nothing. Both would otherwise fall through to the bounding-box path, which places the part plausibly and wrongly — harder to notice than a refusal that names the missing argument. The one case that survives to the solver is a connector deleted *after* the mate was made; the component is then left where it was rather than placed by an invented equivalent, because a revolute is not "concentric, roughly".
- **The frame is orthonormalised on read.** `z_axis` is the mate axis and wins; a skewed `x_axis` is projected off it. Accepting the pair as given makes the third axis non-orthogonal and every rotation derived from it a shear. An `x_axis` parallel to the mate axis says nothing, so a perpendicular is chosen — deterministically, or the part turns on reload.

`assembly_mates._euler_degrees` inverts `sdf._euler_matrix`'s `Rz @ Ry @ Rx`, written out rather than pulled from a library because getting the convention wrong is silent: the part lands somewhere plausible and only a non-axis-aligned mate shows it.

**A component is a reference, not a copy, so `assembly_service.add_component` refuses a part the assembly's owner cannot open.** Checked in the service rather than at each caller because the consequence is not cosmetic: an assembly holding someone else's document reads its geometry straight back out through the BOM and the interference check. Legacy assemblies carry no owner and are left alone, exactly as `can_access` treats their documents.

**The standard parts are generated from the published standards, not downloaded.** `services/parts_catalog.py` builds 210 purchased parts — ISO 4762 socket screws, ISO 4032 nuts, ISO 7089 washers, ISO 2338 dowel pins, ISO 15 ball bearings, NEMA ICS 16 steppers, T-slot extrusion — as ordinary feature trees. McMaster-Carr was the obvious source and is not available to this system: `robots.txt` disallows `/catalog/*` and the API is gated behind a per-customer client certificate. Five things follow:

- **A designation, never a part number.** Nothing here was verified against a supplier's catalogue, and a part number is what an order is placed against. `supplier_search` links a *search* on the designation, which is the thing that actually gets ordered.
- **Fidelity is declared, before you place a hundred.** `fidelity` is `as-standard` or `envelope`; a screw has no thread helix, which is the right body for clearance and interference and the wrong one for a thread study.
- **Where the envelope misleads, the published mass is carried.** A stepper motor's solid envelope weighs far more than the motor, so `typical_mass_g` states the real figure rather than a density being fudged to make the volume come out right.
- **`insert_standard_part` reuses one document per (key, owner)**, so eight screws are one BOM line of qty 8 rather than eight lines — and `standard_parts.document_for` creates it under the *assembly owner's* account, because `add_component` refuses a part its owner cannot open.
- **`clearance_hole` takes `screw`, not `size`.** ISO 273: an M4 gets 4.5 mm, not 4. The parameter cannot be called `size` because `units` folds "in metres" into any parameter with that name, and a thread designation is not a length.

`GET /api/documents/meta/standard-parts` is the browsing route as well as the `list_standard_parts` operation — a person opening a *new* assembly holds no id yet, and that is exactly when they reach for a screw.

**The generated catalog is the floor, and a supplier file the user brings is how it grows.** It can build an ISO 4762 M4×16 and it cannot build *this* connector, so `services/supplier_parts.py` files a CAD file the user imported as a purchased part of their own — STEP and IGES exact through `import_service`, meshes voxelised. The portals that could supply those files at scale were checked and **none of them permits it**:

- **3Dfindit / CADENAS.** `robots.txt` disallows this crawler by name, the site answers a non-browser client 403, there is no documented HTTP API that returns geometry (the published interfaces are CAD-host plugins and a C++ SDK), downloads sit behind a login with a 50-a-day fair-use cap, and the models belong to the manufacturers publishing them.
- **TraceParts.** There *is* a real REST gateway (`cadRequest` → a temporary `cadFileUrl`) behind an API key granted after review — and its terms say users "may not i) distribute the Data as part of an external service, or ii) copy or post the Data on a website, or iii) distribute the Data on any storage medium whatsoever, or iv) use the Data with the aim of competing with any TraceParts service", nor "use such … files to create catalogs … competing with any TraceParts service". It also requires handing over each downloading user's name, email, company and country, and a "powered by TraceParts" credit. Integrable as a per-user pass-through; forbidden as a seed.
- **The open parts libraries are a copyleft trap.** BOLTS is GPL-3 and the FreeCAD Fasteners workbench is GPL-2. Their dimension tables look like free data and copying them would put this codebase under those licences. The standards themselves are the source, which is what `parts_catalog` already does.

So nothing here calls a portal. `SOURCES` deep-links a *search* on each one — a hyperlink is not a copy — and the user who accepted that portal's terms fetches the file. Four things follow:

- **`geometry` is `exact` or `mesh`, on every row of the listing including the generated ones.** A supplier STEP is a `BrepBodyFeature` whose faces can be filleted and measured; an STL cannot. A field present on only some rows is one a caller eventually reads wrong — same reason `observation.summarize_assembly` states its `kind`.
- **`fidelity` gains a third value, `supplier`**: the manufacturer's own body as published, rather than something measured off a table.
- **Rows are owner-scoped and that is a boundary.** A row names a `document_id`, and `add_component` refuses a part its owner cannot open; `insert_standard_part` resolves a supplier key against the *assembly owner's* imports for the same reason `document_for` creates under that account.
- **One `key` covers both halves** (`standard_parts.document_for_key`, `standard_parts.listing`), so the picker is one list and an agent does not have to know which kind it is holding. `catalog_ref` is set on the imported document too, so eight of them are still one BOM line.

Forgetting a part deletes the catalog row and leaves the document — it may be placed in three assemblies, and the row is a shortcut to placing it again rather than the thing keeping it alive.

**Two ways to run an operation.** `dispatch()` raises a typed `OperationError`; `execute()` never raises and returns the full envelope — `ok`, a typed `error`, a geometry `delta`, the compact `state`, and `warnings`. Anything that needs to *observe* a failure rather than propagate it (an agent loop, a training rollout, the HTTP layer) uses `execute`. `ok` is computed: it was a hardcoded `True` with a single construction site until the envelope landed.

**Failures carry a code, not just prose.** `services/op_errors.py`: `MISSING_ARG`, `BAD_ARG`, `NO_SUCH_DOCUMENT`, `NO_SUCH_FEATURE`, `PRECONDITION`, `EVAL_FAILED`, `UNKNOWN_OP`, `INTERNAL`. They subclass `ValueError`, so the routers' existing `except ValueError` handlers keep working. Pick `PRECONDITION` when the fix is a *different previous step* (a flat pattern on a part with no sheet-metal feature), not different arguments.

**`add_modifier("fillet"|"chamfer")` is an edge treatment, not a smooth blend.** It used to build a `FilletFeature` and wrap the root in it — leaving that feature with exactly one child, and a smooth union of one body is that body, so `resolve_suppressed`'s single-child collapse deleted it before evaluation. The op returned `ok`, a feature id and an unchanged volume; a no-op that reports success is the worst thing this action space can contain. It now builds an `EdgeFilletFeature`/`EdgeChamferFeature` over every edge (`_blend_whole_body`), and without the exact kernel says so as a `PRECONDITION`. `fillet_edges` / `chamfer_edges` / `shell_faces` accept `"all"` in place of an id list for the same reason. Nothing in the catalog constructs a multi-body smooth blend any more, so `decompiler` steps through an inert single-child one and declines a real one.

**The exact edge treatments roll back rather than warn.** `_apply_exact` is the exception to the rule below: a 500 mm fillet on a 50 mm cube has no later step that rescues it, so the edit is undone and the failure is a typed `PRECONDITION` naming the radius — not an `ok` whose volume happens to be zero.

**Where two kernels compute one shape, the arithmetic lives in `geom/`.** `holes.py`, `ribs.py` and `patterns.py` each enumerate a shape once, and `evaluator/brep`, `evaluator/sdf` and (for holes) `evaluator/sdf_native` all read it. This is not tidiness: two transcriptions of the same formula agree on the day they are written, and the differential tests then compare two different parts without saying so. `brep._pattern` used to carry a comment explaining that it picks a single dominant world axis for a circular pattern *because the SDF does* — which is the comment you write after they have already disagreed once. Adding a second variant to any of the three made the split untenable; adding a fourth would have made it invisible.

**A hole is not a cylinder** (`geom/holes.py`). `HoleFeature` carries a counterbore or countersink at the mouth, a conical drill point below the shoulder, `through`, and a thread designation. Three rules hold stored documents still: a hole with every option defaulted is *exactly* one centred cylinder, so nothing already saved changes meaning; **`depth` measures to the shoulder, never to the point**, or adding `tip_angle` to an existing feature would silently raise the flat bottom of every blind hole in the datastore; and **`through` lengthens the far end only**, because extending both would carry the recess out of the material it sits in. A countersink is cut with the whole cone rather than the frustum — below the point where it narrows past the bore, the bore has already removed that material, so the two are the same subtraction and the cone is a shape both kernels already build. `add_hole` places the mouth on the body's own face along the axis when no centre is given; without that a counterbore lands in mid-air. `thread` is a callout, not geometry: a tapped hole is drilled at the tap-drill size (`D - P`, ISO 2306) and the helix is a separate question.

**Draft is exact-only, and it is the treatment for what `dfm` already diagnoses.** `services/dfm_topology` has been *measuring* draft — naming faces that will not release from a tool — since before anything could add any. `DraftFeature` rotates named faces about their intersection with a neutral plane placed at the body's extreme **against** the pull, which is the parting line where a two-plate tool splits; a plane anywhere else resizes the part as well as tapering it, and the resize is the half nobody notices until the first inspection report. There is no field form because the nearest one — tapering the whole body — is a different solid that `dfm_topology` would then measure and disagree with the exact kernel about.

**A rib is dimensioned, not grown to the next face.** `RibFeature` holds tip thickness, height and draft together, which a hand-unioned box cannot: a box does not know it is a rib, so nothing maintains the relationship when the wall thickness changes. "Up to next" needs a face reference and the SDF kernel has none, so a rib built that way would exist on one kernel and not the other — height is therefore a parameter. The solid is a trapezoidal prism, exact on both sides.

**`radius_end` makes a fillet variable, and its absence is load-bearing.** OCC's radius law builds a genuinely different surface from the constant form *even where both radii are equal*, so `EdgeFilletFeature` keeps calling the one-argument `Add` whenever `radius_end` is zero — otherwise every stored fillet would move. OCC's variable-radius solver is also markedly less robust than the constant one: on a plain box it declines the four longest edges while filleting the other eight at the same radii, and neither reversing the edge nor swapping the radii helps. That is reported as itself rather than as "your radius is too big", and falling back to a constant radius was rejected — it would return `ok` for a body nobody asked for.

**A helix is a true helix** (`HelixFeature`, exact-only). The spine is a straight line in a `Geom_CylindricalSurface`'s parameter space, so there is no segment count to pick; `SweepFeature` next door is a union of capsules and facets visibly at any count a document can afford. Two things cost hours and are worth knowing before touching it: **`Bnd_Box` on a swept BSpline bounds the control points, not the surface** — it reports a 10 mm coil as 60 mm across, so verify against the tessellation — and **only Frenet mode places the profile correctly** on a helical spine. The auxiliary-spine modes, `SetMode(gp_Dir)` and plain `MakePipe` all mis-place it; a helix has constant curvature and torsion and its Frenet normal always points at the axis, which is exactly the frame a wound wire keeps.

**A `table` pattern is the kind that makes an arbitrary arrangement recoverable.** `PatternFeature.kind` adds `curve` (instances spaced by equal *arc length* along a polyline, translation only — bolt holes around an arc stay parallel to their axis rather than fanning out) and `table` (the placements listed outright). A table's list is complete: the first entry is the first instance and there is no implicit copy at the origin, because an implicit seed would take explicit control away from the only kind that exists to provide it.

**A tree that does not evaluate is a warning, not a failure.** Binding a feature to a parameter expression before defining the parameter is a supported workflow, and `derived.error` exists precisely so a malformed edit never wedges a document. `execute` reports it in `warnings` and `state.error`. `rollback_on_eval_error=True` opts into the stricter contract an RL environment may want; it is off by default because it breaks that workflow.

**Feature ids are deterministic.** `feature_ops.IdAllocator` assigns the lowest unused `f<n>` for the tree in hand, so replaying an operation sequence reproduces the document byte for byte — which is what makes trajectory replay and the decompiler's verification possible. Never mint an id from the clock or a uuid; legacy timestamp/uuid ids are kept in the allocator's used-set so nothing collides.

**Every operation is recorded when a session is open.** `services/trajectories.py` hooks `execute()` and writes `(goal, obs_before, op, args, result, delta, obs_after)` to a `trajectory` row. Opt-in via `trajectories.recording(doc_id, goal=…)`, so the normal edit path costs one ContextVar read. `services/decompiler.py` goes the other way: it walks any feature tree, emits the op sequence that would build it, replays it and compares mesh hashes — only an exact match is kept, because a demonstration that rebuilds the wrong part teaches the wrong thing.

**The health metric for that half of the system is `decompiler.corpus_report`** (`GET /api/trajectories/corpus-health`): what fraction of the documents that exist become verified demonstrations. Measure it against a corpus that covers every feature type the catalog builds — a corpus drawn only from the starter templates (plate, L-bracket, enclosure, stepped shaft) scores 100% while saying nothing about the rest of the catalog. `by_cause` splits the losses (`unsupported` / `replay_failed` / `geometry_mismatch`); `by_feature` ranks types worst-first, and **`blocking` is the column that matters** — every type in an undecompilable document shows a 0% rate, so a `BoxFeature` next to an `OptimizeFeature` is dragged down with it and the rate alone sends you off to fix boxes. Nothing is recorded by the report: measuring should not also write a few hundred trajectories.

**Every builder takes a `target`, and that is what makes nested booleans recoverable.** `union(plate, subtract(boss, bore))` — a bore through a boss that must not cut the plate under it — is a shape whole-tree generation produces routinely, and no operation could express it while every builder combined with the root. `feature_ops.add_primitive(..., target_id=)` combines with one feature in place instead, and the handler returns `group_id` for the boolean it created or joined. The decompiler emits `{"$step": i}` for the second child and `{"$group": i}` thereafter, so a third body joins that group rather than nesting a fresh pair around the second — same body, different tree, and the tree is what replay compares.

**A spec says what the part was supposed to be; everything else only says the body is well formed.** `services/design_spec.py` holds measurable requirements on `document.spec`, driven by `set_spec` / `get_spec` / `verify_against_spec`, and returns `DfmCheck` rows plus a `score` — the fraction met, which is the reward function. Two rules keep it honest: **every kind is something the kernel can actually measure** (there is no `looks_like`), and **an unmeasurable requirement fails loudly rather than passing quietly** — an unknown kind, a missing bound, a body the exact kernel cannot address all return `fail` with the reason, because a spec scoring 1.0 because half of it was skipped is the worst thing a reward function can do. `hole` counts *cylindrical faces on the body*, not `HoleFeature` nodes: a bore a later boolean swallowed is not a hole, and one inside an imported STEP solid is.

**DFM is measured on the body, not on the mesh that renders it.** `services/dfm_topology.py` casts rays through the exact B-rep for wall thickness, draft, undercuts and 3-axis tool access, counts inner shells for trapped voids, and reads the smallest bore and shortest edge off the topology. `dfm` takes a `process` (`additive` | `milling` | `molding` | `casting`); the additive report keeps overhang/support/quote — honest tessellation questions — and the non-additive ones are topology only, with **no quote**, because there is no cost model for them and an invented number is a signal a model would learn to game.

The measurements are only worth having because of four details, each of which was wrong first:

- **`feature_size` was never about the part.** It reported the shortest edge of a marching-cubes mesh, so it moved with `resolution`. Where the body is exact, `wall_thickness` **replaces** that row rather than sitting beside it — two disagreeing "minimum feature" numbers is worse than one.
- **Samples sit on the surface, not on the triangulation.** This is the one that matters. A chord across a convex face lies *inside* the material, so every escape ray from it starts buried — the outer wall of a plain tube came back as 50% of the part needing 5-axis, and a measured 0.4 mm wall read 0.34 mm. The triangulation now only decides *where* to sample; the (u,v) centroid is evaluated on the real surface for both the point and the normal. An opposing-normal filter was written first to suppress the symptoms and then removed: across nine shapes it never changed a reading.
- **Escape rays start 10 µm off the face.** A ray running along the surface it leaves is tangent to it, and OCC reports the grazing contact as a hit — which called the wall of every through-bore unreachable.
- **A wall parallel to the tool axis is reachable.** An end mill cuts with its flank, so a through-bore is machined by a cutter going down it. Requiring the face to point at the tool called every drilled hole unreachable.

**An export is a resource, not a payload.** `services/artifacts.py` renders `step | stl | pdf | dxf | svg` and returns a **URL keyed by the file's content hash**, served by `GET /api/documents/{id}/artifact/{digest}` under the mesh endpoint's contract — immutable, `private`, 404 rather than different bytes under a digest a client was told to keep forever. Inlining is the mistake P1 undid for the mesh and a STEP body is *bigger* than the mesh was. Two consequences: exporting the same body twice returns the same URL (so a retry is free and a package is cheap to rebuild), and the digest is of the *file*, not of the document — two documents that evaluate to identical geometry still export differently because the STEP header carries the part name. `export` is in the catalog, which closes the last place the UI could do something an agent could not.

**The PDF writer is written here, and that is a departure from the optional-dependency rule.** Every other optional piece (OCP, the LLM, Stripe) degrades to something that still works, and the rule for a renderer that *must* exist would be an honest `PRECONDITION`. `cad_kernel/io/pdf.py` exists instead because the thing being rendered is a drawing sheet — polylines, leaders, hatching and monospaced text on one page — and PDF's content stream is `m`/`l`/`S` and `BT … Tj ET`, so there is no absent case to degrade to. `reportlab` would be 3 MB and a fourth way for a deployment to be half-configured, to draw lines. Three details:

- **`drawing.render_pdf` renders *from the SVG*** (`pdf.page_from_svg`, a deliberate subset parser over the closed vocabulary `drawing.py` emits), so sheet size, scale, placement and the title block are decided once and the PDF cannot be a different drawing from the one on screen — the same reason `_dxf_layers` shares the `_Sheet`. Unlike the DXF it carries the text: a DXF goes into a tool that re-dimensions anyway, a PDF is read by a person.
- **The stylesheet is parsed out of `_STYLE`, not restated.** A dash pattern written twice ends up dashed in the SVG and solid in the PDF, and nobody notices until a shop reads a hidden line as an edge.
- **Courier is a base-14 font with an exact 0.6 em advance**, which is what makes `text-anchor="middle"` truthful rather than a guess at substituted metrics. PDF also counts *up* the page in points, so every coordinate is flipped and scaled — the same flip `io/dxf` makes.

**A release package is built from the revision, not from the document.** `services/release_package.py` puts the STEP body, the drawing as PDF and DXF, the mesh, a one-line BOM, the spec report and the revision letter in one zip. A package pinned to "now" is a screenshot of a moving target, so the revision's *feature tree* is evaluated — materialised as an ephemeral document at `{doc_id}@{letter}`, because every reader downstream (drawing, DFM, spec) is keyed by document id and the alternative is threading a tree through nine call sites. `document_service.EPHEMERAL` keeps it out of the datastore, and the guard is inside `_persist` because the evaluate path persists from four places. The manifest states `document_matches_revision` explicitly — a document that has moved on since the release is the normal case. A format that will not render is recorded in `unavailable` rather than being fatal: a body the drawing pipeline cannot trace still has a STEP file worth sending. It runs as a polled job (`POST /{id}/package`) because a package is a fan-out of every slow thing in the system. `quotes.place_order` attaches the same package, and an order on a part with no released revision says so in `package_note` rather than being refused — a prototype is a real thing to order.

**A toolpath is verified against the part, not simulated.** `services/cam/verify.py` cuts the stock with the planned passes and compares the remainder with the finished body: **gouge** (part material the cut removed — a scrapped part, so a `fail`) and **leftover** (stock still standing that is not part). Material removal is a geometry problem with no forces in it, which is why NVIDIA's Newton was investigated and declined — see `docs/CAM-SIMULATION-SOURCING.md`. Three details: it reads `toolpath.plan_passes`, the same passes the G-code is written from, because a verifier checking a *different* path would report a clean cut for a program that gouges; a flat endmill cutting top-down means a point is removed exactly when it sits at or above the **lowest level that cleared its (x, y)**, so the whole swept volume is one 2D floor array rather than a solid per segment; and the reading is correctly insensitive to **stepdown** — intermediate levels change the cutting load, not the geometry left — while stepover and diameter do move it.

**Verifying geometry** is `services/geometry_check.py` (watertight, winding, volume, connected bodies — via `trimesh`, which was a dependency long before anything used it for this) and `drawing.check_drawing`. Both return `DfmCheck` rows so they render and score like the manufacturability checks.

**A part may legitimately be several disjoint solids, and says so through the spec.** Volume, mass and the bounding box were always right across them — they are sums and unions — but "2 disconnected bodies" could not be told from "the part fell in half". The `bodies` operation (`geometry_check.bodies_of`) lists each solid largest-first with its own volume, size and position, plus `largest_fraction`: an accidental severing leaves one big piece and slivers, two intended parts do not. Intent is declared with a `bodies` requirement in `set_spec` and `check_geometry` reads it from there rather than taking a second flag — one place for "what the part is supposed to be", so there is no second place for the two to disagree. Declaring it does not switch the check off: a part short of its declared count still warns and names the number asked for.

**`simulate` is a real solve now, and says so when it isn't.** It was kept out of the catalog while `_approximate_simulation` was all there was — `total_force / volume^(2/3)` clamped to [0.01, 500] MPa, which cannot tell a cube from a cantilever, and a verifiable signal that means nothing is worse than none because a model will optimise it. `services/fea.py` is an 8-node hexahedral linear-static solve reusing `simp_optimizer`'s element stiffness, DOF map and solver — SIMP has been assembling and solving this system all along; what it never needed was **stress**, so the added part is strain and Cauchy stress at each element centroid. The estimate survives as a labelled fallback: `solver` says which ran and `estimate_only` marks it, because the alternative is a meaningless number being scored as a measurement.

Five things there are load-bearing:

- **A body with no distance field is solved from the B-rep, not from a voxelised mesh.** `fea._occupancy_field` falls back to `BRepClass3d_SolidClassifier` (~30 µs a point, agreeing with the analytic path to 0.003%). Without that fallback, every part carrying a real edge fillet, chamfer, face shell or imported STEP solid — the whole point of the exact kernel — got the closed-form estimate instead. Voxelising the tessellation the way `drawing._field` does was tried and is wrong here: `trimesh.voxelized().fill()` marks every voxel the surface crosses, so the body comes back dilated by one voxel all over (4% heavy at the element pitch, **11%** at four times finer, because the shell stays one voxel thick however small the voxel is). A drawing can absorb that — it only traces an outline — but mass feeds straight into stress.
- **Loads and supports act over a patch of fixed physical size** (5% of the body diagonal), not one node. A point force on a continuum is a singularity: applied at a node, a 200×20×20 cantilever's tip deflection went 1.40 → 1.72 → 2.11 mm across three refinements, *away* from the 1.0 mm beam formula. Patched, it converges to 0.854 mm — and that figure is right, because the patch clamps ~10 mm of root and 200·0.95³ = 0.857.
- **The safety factor comes from the peak element stress, not the percentile.** `stress_p99` is the stable number and the tempting one to headline, but it sits *below* the real stress, which pushes the factor up. An optimistic safety factor is the one failure mode this must not have; on a voxel mesh the peak overstates, so the factor is conservative.
- **Above 20k free DOFs the direct solve is abandoned for Jacobi-preconditioned CG.** A sparse LU fills in badly in 3D — a 98k-DOF beam ran five minutes and 5 GB before being killed, where CG is seconds and O(n) memory.
- **CalculiX was considered and rejected.** It is an external binary a deployment either has or doesn't, and every optional dependency here (OCP, LLM, Stripe) degrades to something that still works. An analysis that silently disappears in production is worse than one with a documented discretisation caveat.

**Walking a serialized tree** goes through `core/feature_tree`: `node_children`, `walk_nodes`, `find_node_by_type`, `root_of`. Children live under `params.children` — every hand-rolled walk that reached for a top-level `children` key has been a bug.

**Resolving one for evaluation goes through `document_service.resolved_tree`, and only that.** Suppression → sketches → datums → parameters, in that order. Five copies of the sequence had grown (evaluate_document, interference, slicer, drawing, profile_cut) and a sixth is how a document evaluates to one body in the viewport and a different one in the slicer.

**The native SDF sampler is built by the image now, and never was before.** `backend/native/forge_sdf` is a Rust reimplementation of the grid sampler, selected at runtime by `evaluator/sdf_native` when the wheel is importable. It is 3-30x faster than numpy on the same trees and produces **bit-identical meshes** — `tests/test_sdf_native_parity.py` compares mesh hashes across 15 trees, because two evaluators for one field is a correctness hazard before it is a speedup: a document that meshes one way with the wheel and another without breaks the property the whole cache rests on. Nothing built it: the only instruction was a `maturin develop` in a README, so a 3-30x fast path had existed for programmes without once running in a deployment. The `native` stage in the root `Dockerfile` builds it, permissively — a wheel that will not install logs and is skipped, because `sdf_native` already falls back.

Two things to know before expecting a speedup. **With OCP installed the common case never reaches it**: `evaluate_feature` tries B-rep first, so a box, a plate, a bore all report `sampler: brep` and the numbers are irrelevant to them. What it accelerates is what B-rep *declines* — smooth `FilletFeature`/`ChamferFeature` blends between bodies, `ShellFeature` — plus every deployment without OCP. And a first benchmark of it measured brep-against-brep and concluded Rust was no faster; the toggle was doing nothing. Force `brep.AVAILABLE = False` to compare the samplers, which is what the parity test does.

**One device decision and one sparse solve, in `services/compute`.** SIMP and `fea.solve` assemble the same symmetric-positive-definite `KU = F`; SIMP had a torch CG that used a GPU when there was one and FEA had a scipy CG that could not, so the analysis a user waits for was the half pinned to the CPU. Both now call `compute.pcg_solve` on `compute.device()`. `FORGE_DEVICE` pins it (`cpu`/`cuda`/`cuda:1`), which is how a deployment forces CPU and how the GPU branch gets exercised deliberately rather than only where a machine happens to have one. The iterative path reports the device in `solver`, so two runs on different hardware can be told apart. Two details: non-convergence **raises** rather than returning a plausible vector, because an unconverged displacement becomes a stress and then a safety factor and that is the one output here that must never be quietly optimistic; and the direct solve stays for systems under `ITERATIVE_ABOVE_DOF`, where a factorisation is exact and faster. **The CUDA branch is unverified by execution** — it is the CPU path with a different `torch.device`, which is why it is written that way, but no GPU was available here.

**Generative optimization is async + in-memory.** `POST /api/documents/{id}/optimize` spawns a FastAPI `BackgroundTask` and returns a job id; the frontend polls `/api/documents/{id}/optimize/{job_id}`. Jobs live in a bounded process-local dict in `routers/documents.py`. The actual work is `services/simp_optimizer.py` — a real SIMP compliance-minimization solve on a hexahedral voxel mesh (density ops use PyTorch/CUDA when available; the sparse linear solve uses scipy). The result folds back into the tree as an `OptimizeFeature` and stays editable.

**Text-to-CAD needs a model, and there is no fallback.** `services/text_to_cad_engine.generate_part_tree` (reached from `document_service.create_document(prompt=…)`) asks the LLM for a whole feature tree, builds and meshes it before saving, and makes one repair pass with the concrete error fed back. With no key it raises `TextToCadUnavailable`, surfaced as a `PRECONDITION` carrying a `remedy`; `text_to_assembly` raises the same thing for the same reason, and its job carries the remedy too.

There *was* a 487-line rule-based parser behind this and removing it was the point. It read dimensions out of a prompt and emitted a primitive, so a prompt describing a real part came back as a box with roughly the right bounding volume and none of the described features — indistinguishable from success by looking, and recorded with `source_prompt`, so the training corpus filled with (prompt → unrelated box) pairs that are worse than no data. A generator that silently substitutes a different part is worse than one that says it cannot help.

That is only defensible because the credential-free path to a part is now a real one: an empty document opens on the template gallery and every template is an operation sequence. Two consequences for tests — `conftest.http_part` builds a body over HTTP in two calls where a prompt used to do it in one, and `conftest.whole_tree_document` installs a tree directly for the handful of tests whose subject *is* a document that operations did not build (the decompiler's, chiefly). `text_to_assembly.create_assembly_from_prompt` now takes `build_part` as well as `planner`, so assembly composition — one document per distinct part, instances sharing it, mm placements landing in metres — is testable without a key at all.

Note this path emits a **whole tree in one shot** — it never touches the operation catalog, so it produces no tool-use data. `services/decompiler.py` is the bridge: it recovers the op sequence for any such tree and verifies it by replay. The document keeps its `source_prompt`, which is what makes the recovered sequence a training example rather than a log.

**No canned shapes in the parser.** It reads dimensions, never subject nouns. A hardcoded "RC chassis" used to short-circuit any prompt containing `chassis`/`rc`/`rally`/`buggy` and return a fixed plate — and because `"rc" in prompt` is a substring test, *circle*, *arch*, *torch* and *force* all triggered it too. Adding a shape shortcut keyed on a word is how that happens; parse the numbers instead.

**Image-to-CAD mirrors it.** `services/image_to_cad.py`: a vision LLM builds the tree when configured, otherwise `trace_to_tree` thresholds the image (alpha channel wins when present), contours the silhouette, and extrudes it with interior contours subtracted as holes. Output is an ordinary editable tree — deliberately *not* an `ImportFeature`, which is an opaque voxel body. It never infers depth from a single view; thickness is a parameter.

**Import has two paths, and which one runs decides what you get.** `services/import_service.py`: **STEP and IGES go through OpenCascade** (`cad_kernel/io/step_import.py`) and stay exact — the body arrives as a `BrepBodyFeature` carrying serialized OCC geometry, so its faces and edges are addressable, `mass_properties` is computed rather than sampled, and it re-exports as an editable solid. Meshes are voxelized into an `ImportFeature`, because an STL has nothing better to recover. STEP falls back to the mesh path when OCC is absent or the file defeats it; IGES has no fallback and says so.

Three things there are load-bearing:

- **Units come from the file's header, not from the mesh path's `extent > 5 m` guess** — which reads a 3 mm cube as a 3 m block. An explicit `units` argument still overrides, reinterpreting the file's raw coordinates.
- **`xstep.cascade.unit` is read through a *cached* global that `STEPControl_Writer` resets to millimetres.** So a read after any export came back 1000× too large with the static still reading `M`. Both sides are now pinned per call: the reader via `STEPControl_Reader.SetSystemLengthUnit`, the writer via `model.SetLocalLengthUnit(1.0)` / `SetWriteLengthUnit(1.0)`.
- **A result that is not a closed solid with positive volume is refused.** OCC will read a file it only half understands and hand back a few loose faces — which looks like a body, measures as nothing, and would displace a voxel import that worked. IGES sewing runs at 10 µm for the same reason: at 1 µm a plate's bore is left unsewn and the shell closes over it, giving a solid plate with no hole.

**The action space is described in one place, and it is the schema.** `services/action_space.py` generates the copilot's system prompt, the function-calling `tools` payload and the training corpus's system prompt. There were three generators; the corpus and the prompt agreed only by coincidence, and both handed a model **parameter names and nothing else** while `op_schema.tool_definitions` — the one thing a constrained decoder can be pointed at — was served on an endpoint nothing used. That split has a specific cost: the corpus is training data, so a corpus describing a different action space from the one used at inference teaches a model to drive an API that does not exist. `llm_client.supports_tools()` decides which form goes out (`FORGE_LLM_TOOLS=0` forces the prose one), and the decision records `_via` so a benchmark can tell a schema-constrained call from a parsed one.

**The schema is enforced all the way down.** `op_schema._check_nested` descends into declared `properties` and honours `additionalProperties: false`. It did not, and that was the largest hole in the surface: `add_primitive` with `{"width": .1, "depth": .06, "thickness": .008}` had all three invented keys dropped on the floor and returned a **default 50 mm cube** as `ok: true`. Only where a shape is *declared* — `add_sketch.sketch` is an opaque object the sketch solver owns, and a check invented here would be a second, weaker definition of a sketch.

**Metres in, millimetres out — `services/units.py` is where that is said.** The kernel is metres; the observation an agent reads back is millimetres (`bbox_size_mm`), so on every call a model reads `100.0` and must write `0.1`. Units are declared by parameter *name* (`UNIT_BY_NAME` / `UNITLESS` / `COMPONENTS`, a component taking whatever its vector means) and folded into descriptions at catalog build, so the prose cannot drift from the code — twenty length parameters previously stated no unit anywhere. Two strengths, deliberately different: `exclusiveMinimum: 0` goes **into the schema**, because a zero or negative length is impossible; the magnitude band is only a **warning**, because a 2 m sheet is a real part and a hard bound would refuse real work. `test_action_space` fails on any parameter name that is in neither map, so a new one must be classified rather than defaulted to silence.

**A default is the answer a caller would have chosen; anything else is an invention reported as a success.** `add_extrude {"depth": 0.008}` built a 50×30 mm rectangle nobody mentioned and returned `ok`. `_one_of` refuses when no geometry is named — extrude/revolve/sweep/loft — as a handler-level check, because a JSON Schema `required` list cannot say "profile *or* sketch". Dimensional defaults stay: a box with a default size is still a box.

**Every failure carries a remedy, not just a code.** `op_errors` attaches one per code — `MISSING_ARG` → supply it, `PRECONDITION` → a different *earlier* step, `NO_SUCH_FEATURE` → `list_features`. `fillet_edges` already did this inside its message and was the exception; this makes it the rule without every handler remembering.

**The copilot checks the spec before it says done.** `_unmet_requirements` runs `verify_against_spec` on the transition to done and feeds the failures back — once, because re-checking after every edit spends the budget checking and a second refusal is a loop rather than a correction. `run` returns `finished` and `unmet`, and a run that stops short says so in its summary rather than reading the same as one that succeeded.

**`evals/` is whether any of it works.** `evals.agent` runs a goal, then scores the body with `verify_against_spec` — the reward function, not a second opinion, and never an LLM judge. `evals.tasks` holds two suites: goal tasks that need a key, and **adversarial** tasks that replay a known mistake and assert what the API does about it (`expect="refuse"` / `"warn"` / `"succeed"`). The adversarial suite needs no key and runs in `tests/test_agent_eval.py`, so the harness cannot rot. Resolution is pinned through `rollout.rollout` — `capped_resolution` clamps to the account's plan, so an unpinned benchmark scores differently depending on who ran it. The headline is **caught**: of the calls that should have been rejected, how many were. It went 0/5 → 5/5, and every one of those five previously returned `ok: true` with a body nobody asked for.

**Materials are one catalog.** `services/materials.py` is the single source (43 grades across 12 categories, each tagged `tier: maker|professional`). Properties are SI throughout; `to_spec_material()` converts to the MPa/GPa view the solver schema wants — never hand-convert at a call site. Material ids are persisted on documents, so **existing ids are never renamed**.

**A sketch reaches the kernel as curves, not as a ring of points.** `sketch_solver.sketch_to_loops` emits `{"type": "loops", "loops": [{"curves": [...]}]}` — `line`, `arc` and `circle` — and both kernels build from it (`evaluator/sdf.profile_sdf_2d`, `evaluator/brep._loops_faces`) for extrude, revolve and ruled loft. `sketch_to_polygon` is still there and unchanged: documents persisted with `{"type": "polygon"}` must go on meaning exactly what they meant when they were saved, tessellation included, for the same reason `LoftFeature` was left alone when `RuledLoftFeature` was added.

It matters because the sketch used to be the one path that *downgraded* geometry on its way in. Arcs were tessellated at 24 segments and circles dropped entirely, so a sketched bore arrived as 24 planar faces — invisible to `design_spec._c_hole` (which counts cylindrical faces, deliberately), to `dfm_topology`'s smallest bore, and to `naming`, which handed out 24 tiny face ids where `fillet_edges` needed one. A circle-only sketch, the plainest thing anyone draws, could not be extruded at all.

**Containment is decided in `cad_kernel/geom/profile2d.py` and nowhere else.** Even-odd parity: a point is inside when an odd number of loops contain it, so nesting works to any depth, an island inside a bore is a face rather than a special case, and a loop's winding direction carries no meaning — which is right, because the direction someone happened to draw in does not either. The SDF gets that answer implicitly from parity and the B-rep gets it explicitly from `faces_of`; deriving both from one function is what stops a document meaning one thing with OCP installed and another without. `_loop_wire` takes a *placement function* rather than a plane name, so a revolve's half-plane uses the same builder as an extrude's plane. A line, arc or circle marked `construction: true` is solved and constrained like any other and left out of the profile.

**The solver says what is wrong, not whether it converged.** `converged` is `residual < 1e-6`, which an *unconstrained* sketch satisfies trivially — the same class of bug as the hardcoded `ok: True` the operation envelope was built to kill. It is kept because callers read it, and `sketch_solver.diagnose` sits alongside: `status` (`well_constrained` / `under_constrained` / `over_constrained` / `conflicting`), `dof` (variables minus the Jacobian's rank) and `redundant` (equations minus rank). `add_sketch`/`create_sketch`/`update_sketch` report all of it and refuse only `conflicting`, as a typed `BAD_ARG` naming the constraints — under-constrained is the normal state of a sketch someone is drawing, and refusing it would make the canvas unusable. `check_sketch` asks the same question without changing anything.

Four details there are load-bearing:

- **Rank is read off a *row-normalised* Jacobian.** Residual rows are not commensurate — `parallel` is a cross product, `distance` is a length, `angle` is radians — so a metre-to-millimetre rescale moves them by different factors and an absolute tolerance changes its mind about the same sketch. Normalising per row cannot change the row space.
- **A conflict is named exactly; a redundancy names a group.** Rows with a residual are the conflict, which is precise. Redundancy is a property of a *set*: every member of a dependent cycle is individually removable, so "these five constraints carry four constraints' worth of information" is the true statement and picking a culprit would be an invention. The group is ordered by null-space weight.
- **`fixed` emits one row per axis given.** It used to default a missing axis to the point's *live* coordinate — a residual that is identically zero with a zero derivative, pinning nothing while still counting as an equation, so pinning only `y` reported a phantom redundancy.
- **Curve-to-curve tangency has two answers.** External is the default (a rounded slot, a dogbone, a belt path); `internal: true` asks for the other.
- **The sketch is compiled once, and the Jacobian is sparse.** `_compile` resolves every constraint into a closure over *variable indices* plus the columns it reads; the entity tables used to be rebuilt inside every residual evaluation, which was 91% of a solve. The columns are what make the Jacobian cost two evaluations per nonzero instead of `2 x variables` full ones — 18-112x end to end, and the difference between linear and quadratic in the sketch size. A hand-written column set that misses an entry is a silently wrong rank, so `test_every_constraint_type_declares_the_columns_it_reads` compares the sparse matrix against a dense one across all 18 types.
- **The sketch bound is on `entities × constraints`, and it is a security bound.** The rank comes from an SVD, which is O(rows² × variables), and `_redundancy_groups` asks for the full left basis, which allocates rows². The operation surface is reachable by anyone who can open a document and `routers/operations` allows 300 calls a minute, so an unbounded spec is a CPU and memory denial of service. Two counts were the wrong shape for it: measured, a 601-entity chain costs 0.41 s at one constraint per segment and **2.24 s at three**, so the cost tracks the *product*. The old 600/600 pair was about right for the dense case, which meant a 1500-point traced outline — cheap, and the thing people actually wanted — was refused on a number tuned for something else. `MAX_SOLVE_WORK` (600k units ≈ 2.2 s) is the real bound; `MAX_ENTITIES`/`MAX_CONSTRAINTS` stay as generous per-axis stops. `size_warning` is a band at half the budget, surfaced as `size_note` on the operation result — the sketch that gets refused is usually the one after the one that took four seconds.

**A sketch is a feature, and it builds no body.** `SketchFeature` (`ops/sketch.py`) holds the spec, the profile it solves to and where it lives; `create_sketch` makes one and `add_extrude`/`add_revolve`/`add_loft`/`add_ruled_loft` take `sketch`/`sketch_a`/`sketch_b` in place of a profile. `feature_ops.resolve_sketches` substitutes it into whatever reads it and *takes it out of the tree* before anything evaluates, so booleans, the mesher, the bounding box and DFM go on seeing the tree shape they always saw. The profile is substituted rather than copied, which is what makes the sharing real: a copy passes every geometric assertion on the day it is made and drifts apart on the next edit. A sketch nobody reads simply disappears from the evaluation tree, leaving the same placeholder an all-suppressed tree gets.

**A new document is three datum planes and no body.** It was a 100 mm box flagged `placeholder`, quietly replaced by the first real feature — which meant the viewport opened on a part nobody asked for, and predicting what `add_primitive` would do required knowing about a flag. `DatumPlaneFeature` (`ops/datum_plane.py`) is the same bodyless-feature contract `SketchFeature` has: it lives in the tree, `feature_ops.resolve_sketches` prunes it out via `BODYLESS_TYPES` before anything evaluates, and its `evaluate` raises rather than returning an empty solid that would delete the body beside it. They are ordinary features — `delete_feature` removes one, `add_plane` puts one back at any orientation and offset, and `list_planes` reads them. Five things follow, each of which was wrong first:

- **A document with no body reports none.** `resolve_for_evaluation` hands the evaluator a 1 mm stand-in when the tree prunes to nothing, because the pipeline needs *a* solid — but reporting that as the document's geometry puts a confident little cube in the viewport, scaled to fit, which is the starting block all this replaced. `evaluate_document` short-circuits on `feature_ops.has_solid` and records no mesh, no bbox and no error. `bounding_box` still answers in its usual shape, with zeros and `body: false`.
- **Cutting nothing is refused.** After pruning, `subtract(∅, tool)` collapses to its one surviving child, so a first-op subtract would return the *tool* as a solid and report success. `add_primitive` raises `PRECONDITION` — in `feature_ops`, where every caller passes.
- **The decompiler treats the default three as the starting state, not as steps.** Replay runs into a *new* document, which already has them; emitting `add_plane` would rebuild the source with six, and the verification could never catch it because planes carry no geometry and the mesh hashes would match. A plane at a non-zero offset, or a second one on an orientation, is emitted.
- **`placeholder` is still honoured on read.** Nothing creates one, but they are persisted, and without that branch a legacy blank document's first edit unions with a stray 100 mm block.
- **Anything that evaluates a raw tree had to be found.** `run_document_optimize` was the sixth copy of the resolution sequence and now goes through `resolved_tree` like everything else; `_optimize_feature_scope` skips bodyless leaves, which are leaves with no extent to audit.

**A starter part is an operation sequence, not a serialized tree.** `services/templates.py` holds four — plate, L-bracket, open-top enclosure, stepped shaft — each a list of `{op, args}` run through `decompiler.replay`, with the same `{"$step": i}` references a recorded trajectory uses. `apply_template` builds one and `list_templates` browses them; `frontend/src/components/EmptyDocumentGuide.tsx` is the gallery, drawn only while the document has no solid, so the first feature is the last frame it renders. Three properties follow from being ops rather than a tree, and none survives a hand-written one: a template can only build what the catalog can build, applying it inside a recording session writes a real trajectory, and the gallery button and an agent run the identical sequence. `apply_template` refuses a document that already has a body — it combines with the whole part and rebinds names like `length`, so it is a starting point or it is nothing.

**Parameters are bound in a second step, and that is not a workaround.** `add_primitive` takes `params.size.x` as a *number* and `op_schema` enforces it, which is right — the schema is what a constrained decoder reads. So a template builds with the literal and then rebinds through `set_feature_params`, whose `params` is an opaque object the feature owns. `test_templates` re-sets each template's parameters to the values they already have and re-measures: the literal and the expression must say the same thing, or the body jumps the first time somebody touches a number.

**The decompiler recovers parameters, and could not before.** The stored tree holds `"=length"`, so the emitted `add_primitive` carried a string into a numeric field and the schema correctly refused it — every document with design intent in it was recorded as `replay_failed`, which templates would have made the common case. `decompile_document` now decompiles the *resolved* tree, prepends `set_parameters` and appends the bindings; `_shift_refs` moves every `$step`/`$group` along, because a reference counts from position zero and an unshifted one targets the step before the one it means — a valid op on the wrong feature, which replay would happily perform. Verification resolves each side against its own parameter table.

**`derived.numeric_tree` is the tree to read as geometry.** `feature_tree` keeps the expression, because that is the design intent and the inspector shows it; snap points, selection outlines and a sketch plane's face offset need the number, and the first template crashed the whole viewport on `q.z.toFixed is not a function`. `document_service._numeric_tree` substitutes the values and changes nothing else — same nodes, same ids, unlike `resolved_tree`, which also prunes — and it is absent when a document has no parameters, so the common case pays nothing. `frontend/src/util/featureTree.geometryTree` is the one place the client chooses between them; a client resolving expressions itself would be a second evaluator drifting from the one that produced the body on screen.

**The prompt bar edits the open part.** It only ever called `createFromPrompt`, so typing a change to what you were looking at silently *replaced* it with a new document. With a body on screen the primary action is `ai_edit` and "New part" is spelled out beside it.

**Sketch-on-face has two forms and the exact one stores a descriptor.** `on_face` takes `{feature_id, face}` — symbolic, six bounding-box extremes, `services/datum.py`, and the only thing that works when the body has no exact form — or `{feature_id, face_id}` naming a planar face from `list_faces`, resolved through `naming.resolve_references` so it follows a resize and reports `split`/`deleted`/`unresolved` rather than sliding onto a neighbour. What is *stored* is the whole descriptor, not the id: an id is a hash of the face's current measurements, so the first version of this lost the face on every resize. `list_faces` takes an optional `feature` for the same reason `resolve_face_frame` evaluates only the referenced subtree — a sub-body's face ids are its own, and scoping the reference to a feature keeps the sketch's own extrusion out of the datum it sits on. `check_references` includes sketch planes.

**Sheet metal is modelled as bends, not as a generic solid.** `cad_kernel/ops/sheet_metal.py` holds a base flange plus edge flanges (inside radius + angle), evaluated by `SheetMetalSDF` or, when OCC is present, built exactly by `brep._sheet_metal`. That structure is what makes `flat_pattern()` computable — the developed blank needs bend geometry that can't be recovered from an arbitrary body. Bend allowance uses the K-factor convention. Anything that *cuts* a sheet-metal part must first call `sheet_metal.unfold_tree` (profile-cut and nesting do): sectioning the folded body traces a silhouette that doesn't fold back into the part.

**Drawings: the kernel projects, the caller decides.** `services/drawing.py` takes a `DrawingSpec` — which of the six orthographic views, which section planes and where they cut, what to dimension, what to call out, projection angle, sheet, scale. Projection, section-cutting and hidden-line extraction are pure functions of the body; everything else is a drafting decision and belongs to whoever is driving. It used to be inverted: hardcoded front/top/right, a section pinned to mid-Y, and one boolean for the caller.

**A drawing exports as DXF as well as SVG** (`drawing.render_dxf` → `io/dxf.write_layers`). The SVG is a sheet to read; the R12 DXF is geometry the next tool measures and edits, on `VISIBLE`/`HIDDEN`/`SECTION`/`CUTPLANE`, laid out exactly as the SVG and flipped in Y because DXF counts up the page and SVG counts down. The LTYPE table must precede the LAYER table or a reader silently falls back to continuous — which is how hidden detail ends up looking like an outline. Only geometry crosses over: dimensions and notes would need `TEXT`/`DIMENSION` entities, and a half-transferred annotation is worse than an honest outline.

**A section carries a cutting-plane line on a view that sees the plane edge-on.** Without it a view labelled A-A is a second picture rather than part of a drawing. The line lies *in* the plane, so it runs along the view's other axis and the arrows point along the plane's **normal** — pointing them along the line was the first attempt and says nothing about which way you look. When no drawn view sees the plane edge-on the section reports `marked_on: null` instead of the marker being placed somewhere invented.

Three things there are easy to undo by accident:

- **A body only the exact kernel can build has no field to project.** `_field` falls back to voxelising its mesh through `GridSDF` — the one place a drawing is quantised. It affects only the traced outline of edge-filleted/chamfered/shelled parts; the printed figures come from `derived.bbox` either way.
- **Outlines contour the signed field, never a boolean occupancy mask.** A mask pins the outline to cell boundaries, and where a sample lands exactly on the surface `sdf <= 0` counts it inside and the silhouette gains half a cell — a 35 mm plate-and-boss drew as 35.33 mm.
- **Printed dimension figures come from `derived.bbox`**, not from measuring the traced silhouette, so a drawing and `bounding_box` cannot disagree about the part's size. Dimension endpoints are given in model mm on the view's own two axes, so the figure stays true at any scale.
- **Hidden lines come from `_occluded`**: along each ray, the largest field value between where it enters and leaves the body. Solid all the way through and that stays negative; pass through a void and it goes positive. The `min_gap` floor is load-bearing — without it a ray grazing the surface reads its own boundary sample as a cavity and the view fills with spurious dashes.

**Optimization can be told what not to delete.** SIMP removes any material that isn't carrying load, which routinely eats mounting bosses and bolt-hole walls. `feature_ops.set_keep` flags a feature; `run_simp_from_solid` rasterizes those features onto the element grid and pins them solid (exact geometry, not the sphere `keep_in` regions use, and *not* also a fixed support). Every leaf feature is then audited after the solve, and anything left under `_FEATURE_INTACT_FRACTION` is reported in `info["removed_features"]` — surfaced on the job and persisted on the `OptimizeFeature`, so a part never comes back quietly missing something.

**The mesh is a resource, not part of the document.** `derived.mesh_url` is `/api/documents/{id}/mesh/{mesh_hash}`, served by `routers/documents.get_document_mesh` from an LRU of encoded meshes. It used to be a base64 STL data URI inlined in the document body — 99% of a 1164 KB response, re-downloaded on **every** edit; the same part is now a 1.5 KB document plus a 314 KB mesh fetched once. Four things there are load-bearing:

- **The hash is the identity, so the response is immutable and cached forever.** `Cache-Control: private, max-age=31536000, immutable` — `private` because the endpoint is access-checked and a shared proxy caching it publicly would hand one tenant's geometry to another.
- **A hash the document does not have is a 404, never the current mesh.** Answering with different triangles under a hash that browsers have been told to keep forever poisons every cache that sees it.
- **A superseded hash still resolves while it is remembered.** Two edits landing close together leave the client holding the older URL; the mesh it names is still exactly those triangles, so serving it is correct. `frontend/src/util/forgeMesh.fetchForgeMesh` re-reads the document once on a 404 for the case where it has fallen out of the LRU.
- **The wire form is indexed and normal-free** (`cad_kernel/io/mesh_binary.py`, `"FMSH"`). STL is triangle soup with a per-face normal three.js recomputes anyway: 872 KB where the same mesh indexed is 314 KB. STL is still what `export` writes — that is an interchange format, this is a transport.

**A library card is a picture of a *body*, not of a document.** `services/thumbnail.py` renders a shaded three-quarter view in numpy — painter's algorithm, back faces culled by screen-space winding, no GPU and no browser — served at `/api/documents/{id}/thumbnail/{mesh_hash}` under the same immutable caching as the mesh, and 404 on a hash the document does not have. Keyed on the document id it would confidently show last week's part, which is worse than the generic icon it replaced; that identity only exists because the mesh got a content hash first. Four things there are load-bearing:

- **The normal carries the tone and depth only grades it** — the opposite of `features/sketch/PartBackdrop.tsx`, and for a reason. The backdrop looks straight down a plane normal, where every visible face is parallel and the Lambert term is useless. A three-quarter view sees three differently-oriented sides. Leading with depth put a diagonal seam across every flat face, because `tri_depth` is a per-triangle mean and the two triangles of one rectangle do not share it.
- **Z up, not the viewport's camera.** three.js is Y-up and the viewport simply accepts that; copying its camera lays the part on its side and points a boss at the lens where it cannot be seen.
- **The frontend cannot use a plain `<img src>`.** The endpoint is access-checked and the session is a bearer token; a token in the query string would authenticate the request and put a credential in every referrer and proxy log. `components/Thumbnail.tsx` does an authed `fetch` to a blob URL — the HTTP cache still serves the second visit, because the response is immutable.
- **Lazy at the card, not at the image.** `loading="lazy"` would still issue the request, and the *render* is the expensive half. An IntersectionObserver means a library of fifty parts renders the dozen on screen, and a missing picture falls back to the icon silently.

**The listing extracts what the card shows in the SQL pass it was already making.** `persistence.list_document_summaries` reads lifecycle state, material, mass, the latest revision letter, `mesh_hash`, `created_at` and `source_prompt` with `json_extract`/`->>`, never deserializing a feature tree. `document_service.list_documents` overlays live in-memory documents on those rows and must fill **the same fields on both paths** — two paths producing different cards is how a field silently only works after a restart. The library searches the prompt and the material as well as the name, because `source_prompt` is often the only thing anyone remembers about a generated part.

**Below 1024 px the editor is one column with a switcher, not three squeezed ones.** `hooks/useNarrow` is a `matchMedia` query (it fires when the answer changes, not on every resize frame); `EditorScreen.Column` wraps each of the three panes **always**, at `display: contents` when wide — so crossing the breakpoint hides and shows columns instead of re-parenting `DocumentViewport`, which would tear down the WebGL context and lose the camera.

**Clicking the body names a feature, and it is not a guess.** The mesh carries one feature id per triangle (`services/picking`, shipped in the FMSH owner block at four bytes a triangle). On the exact kernel it is read straight off the tag of the OCC face the triangle was meshed from — the triangle either came from that feature or it did not. On the SDF kernel there are no faces, so the question goes to the fields instead: the leaf whose own distance vanishes at the triangle centroid is the leaf that put it there, and a centroid no leaf vanishes at is left **unowned** rather than attributed to whatever was nearest. `pickFeatureAt` in the frontend is the old nearest-analytic-proxy guess and is now only the fallback for a body that could not be attributed.

This is the opposite call from the *face* picker, and the difference is real: `Kernel.from_mesh` gives one `Face` with `surface=None`, so no triangle can name a face — but every triangle can name a feature.

Three things there are load-bearing:

- **Provenance comes out of the tessellation that already ran.** `Kernel.evaluate_feature` keeps the history from `build_with_history` and calls `tessellate_owned`; re-deriving it afterwards would mean meshing the body a second time (280 ms).
- **`tessellate` meshes a copy, so the owners are mapped through `BRepBuilderAPI_Copy.ModifiedShape`,** not by assuming the copy explores its faces in the same order.
- **A misaligned owner array is worse than none** — it selects the wrong feature — so `write_mesh_binary` drops a list whose length does not match the triangles, and `NO_OWNER` (`0xFFFFFFFF`) is a real answer rather than table slot 0.

**Undo is local; the server catches up afterwards.** `useDocumentStore`'s history holds `{tree, derived}`, not the tree alone — which is why undo used to be as slow as the edit it reversed, the tree coming back instantly and the body not. Since the mesh became an immutable hash-keyed URL the browser already holds, restoring `derived` alongside the tree puts the old body back with no evaluation at all (measured: 400 ms to the restored volume, versus a full round trip). Everything *measured from* the geometry still goes stale — `derived` is the body's own cache, a simulation or a DFM report is a reading of a body no longer on screen. The write to the server runs in the background and only adopts its response if the tree it sent is still current; `historySyncSettled()` is what every mutating action awaits, so an edit issued during that window cannot land before the undo it follows.

**A viewport drag is one operation, committed on release.** `MoveHandles` previews by moving the *selection outline* — moving the rendered mesh would be a lie, since one feature is moving and the union of it with everything else is not that mesh translated — and commits a single `set_feature_params` when the pointer comes up. Committing per mouse-move would be hundreds of round trips and, worse, hundreds of rows in the trajectory recording: a corpus in which moving a boss takes 300 calls teaches that. Two details are not optional: the pointer target is a fat invisible cylinder around the thin arrow (a missed grab does not do nothing, it orbits the camera away from what you were aiming at), and orbit is suspended on **hover** via drei's `enabled` prop, because `CameraControls` listens on the canvas element and an r3f `stopPropagation` cannot reach it.

**The bundle is split at the screen and the panel.** Sign-in stays in the first chunk because it *is* the first paint; the library, editor and assembly screens, the five non-Model panels and the sketch canvas are each their own chunk. 1,435 KB / 388 KB gzip in one file became a 195 KB / 62 KB entry — three.js, the slicer and the drawing viewer now arrive when something asks for them. Every lazy boundary has a fallback that looks deliberate (`Layout.ScreenFallback`); the sketch canvas's is `null`, because it renders nothing until it is opened and a spinner over the viewport for a closed overlay is worse than no feedback.

**An edit that cannot move the body does not rebuild one.** `document_service._evaluation_key` hashes everything that changes what an evaluation would produce — tree, resolution, parameters, configurations — and `evaluate_document` returns early when it still matches. `set_material` and `set_spec` used to pay a full evaluate-and-tessellate (85-90 ms) and re-send the mesh; they are now 14-17 ms and the mesh URL does not move. The key is built by dumping the whole model minus provably-derived fields, not by listing fields to include: the second form is how a later schema addition silently stops invalidating the cache. Mass is the one derived number a material moves, so it is recomputed from the cached volume.

**A subtree's shape is cached by content, so an edit rebuilds the edited node and its ancestors.** `evaluator/brep._NODE_CACHE` keys each built shape on its subtree — the node's own parameters plus its children's keys, recursively, so a parameter substituted into a leaf ten levels down changes the root's key. A feature that will not serialise yields no key and is simply not cached; a miss is slow, a stale hit is a document that quietly stops meaning what it says. `_boolean` additionally keys each **prefix of the fold**, because fusing twelve bodies is eleven booleans and editing the twelfth leaves the first ten results identical — that is what makes editing the last feature of a part cost one boolean rather than all of them. A twelve-feature edit went 467 → 268 ms, and `get_exact_body` after a display build now costs nothing instead of rebuilding the same tree a second time.

Three things have to come back with the shape or the cache is a downgrade:

- **The `EntityMap`.** A cached shape handed to a parent boolean has to answer `_tags`, or `history.advance` sees an untagged input and the whole naming scheme silently degrades to descriptor matching. The map is cached beside the shape, still bound to the `ShapeKeys` it was built under — that map indexes by `IsSame` and the cached shape's sub-shapes are the same ones, so the tags still resolve.
- **The reference verdicts.** `_resolved` files "these four edges matched, that one is gone" on the recorder while the child body exists. A cached subtree never runs it, so the verdicts are replayed from the entry; otherwise `check_references` would report fewer selections the second time a document is built than the first.
- **Meshing is a read, and OCC does not treat it as one.** `BRepMesh` widens edge and vertex tolerances to cover the deflection it achieved, and `BRepTools.Clean_s` does not put them back — so tessellating a body twice at the same resolution returns two *different* meshes. It never showed while every build was discarded after one mesh; the moment shapes are kept it is a `mesh_hash` that drifts for a document nobody edited, which is exactly what P1's immutable mesh URLs cannot survive. `tessellate` therefore meshes a `BRepBuilderAPI_Copy` (1 ms against a 280 ms mesh). `document_service._BREP_CACHE` had been handing out shared bodies all along, so this was latent rather than new.

**The 2D profile field is evaluated where it can matter, and once per distinct point.** Two exact optimisations, neither of which may change a value — `test_sketch_profiles` compares both kernels against closed-form volumes at 1e-9, and `test_evaluation_cache` compares the fast paths against the slow ones with `array_equal` rather than `allclose`:

- **A uniform grid over the curves** (`geom/profile2d._binned_sdf`). A curve is skipped for a cell only when it provably cannot be nearest — its bounding box is further than `D + 2·rad` from the cell centre, where `D` is the true nearest-curve distance there — and provably cannot contribute a ray crossing, which is a rectangle test on the v-range and the right edge. Measured on 300 curves over a 128² grid, that leaves 57 of 300 per cell for a circle and 29 for a lobed outline, and 11 for crossings. The circle is the worst case honestly: points deep inside a ring really are near-equidistant from all of it, and no index conjures locality the geometry does not have. 2.3× at 300 curves.
- **A repeated (u, v) is evaluated once** (`evaluator/sdf._grid_plan`). An extrude asks the same 2D question once per slice: 128³ sample points carry only 128² distinct pairs. The probe is what keeps this from taxing the cases it cannot help — a revolve passes a *radius*, different at nearly every point, and a full `np.unique` over two million of those would cost half a second to learn nothing, so a strided sample answers the same question first.

Together: a 300-curve traced profile extruded through the numpy SDF at resolution 128 went **23.5 s → 0.51 s**.

Parity is additive mod 2, so `sum(count_i mod 2) mod 2` equals `sum(count_i) mod 2` — which is why crossings can be counted over one flat list of curves instead of per loop. `loop_contains` is unchanged and still what `nesting` and `faces_of` use.

**`feature_ops.resolve_for_evaluation` is suppression → sketches → datums on one copy.** Each stage still deep-copies when called on its own, because each is a public entry point handed a document's live tree; run back-to-back the second and third were copying a tree nobody else could reach. `document_service.resolved_tree` is still the only place a document's evaluation tree is derived.

**The CSP hashes the SPA's one inline script rather than allowing inline scripts.** `index.html` carries a `window.onerror` handler that paints a readable failure into `#root` when the bundle itself throws — and `script-src 'self'` refused it, so the only safety net for a white screen was itself dead. Production-only, because the Vite dev server sends no CSP; found by loading the built `dist/` through FastAPI rather than through Vite, which is the only way to see it. `main._csp()` hashes whatever inline scripts the served `index.html` actually contains, so editing the handler cannot silently re-break it. `connect-src` no longer allows `data:`: that was for the STL data URI the mesh used to be, and nothing has fetched one since P1 made it a hash-keyed URL. `img-src` keeps `data:` and `blob:` — the thumbnails are authed fetches turned into blob URLs.

**The abuse surface is bounded at the edge, not in each handler.** Three things a production deployment needs and none of which a handler can do for itself:

- **Body size** (`app/body_limit.py`), as raw ASGI so it runs *before* the body is assembled — a `BaseHTTPMiddleware` receives a request already being buffered, which is the thing being defended against. Every upload route does `data = await file.read()` and *then* checks `MAX_FILE_BYTES`, so the bytes were already resident when the caller was told the file was too large; `POST /op` buffered whatever it was handed, and that endpoint is reachable by anyone who can open a document. The cap is enforced on `Content-Length` **and** on the streamed count, because `Transfer-Encoding: chunked` carries no length. 8 MB for JSON, 56 MB for the three upload paths — one number for both would either refuse real STEP files or leave the JSON surface open.
- **Rate limits** on the operation endpoints, the uploads and the background jobs, not just on auth. Quota metering bounds *mutating* calls per account and does nothing about queries, and an unauthenticated deployment attributes everyone to one shared dev account. `rate_limit._route_key` keys the bucket on the route **template**: keyed on the concrete path the limit was per-document, so a caller only had to walk their own documents to get a fresh bucket. It is in-process, so a second worker doubles every limit — that is on the same list as the other single-worker caveats in `DEPLOY.md`.
- **A startup that refuses an unsafe posture.** `FORGE_AUTH_REQUIRED=1` with no `FORGE_JWT_SECRET` now raises instead of logging an error. The fallback key is per-*process*: with more than one worker a session is valid or 401 depending on which one answers, which is an intermittent logout nobody diagnoses from a line that scrolled past at boot. `FORGE_ALLOW_INSECURE=1` is the documented override.

**An operation is attributed to its caller, and exactly one operation needs that.** `execute(op, doc_id, args)` deliberately takes no account — access is decided at the router against the document, and threading an identity through every handler would put an access decision inside each one. But `list_standard_parts` returns the caller's *own* imported supplier parts, and scoping that to the document's owner leaked their designations, manufacturers and part numbers to anyone they shared a part with. `services/caller.acting_as` is a ContextVar the two op routes set, in the same shape `rollout` and `trajectories` already use. It never widens access — the router has already decided the call is permitted — it only narrows what a permitted call returns, and `None` (a direct in-process call) is a real answer rather than an invented identity.

**Anything a user names can reach a renderer, so it is escaped where it is written.** `drawing._esc` covers quotes as well as angle brackets, because the gap between "this is a text node" and "this is an attribute" is one refactor wide and `MakePanel` renders the sheet through `dangerouslySetInnerHTML`. A section's label (`DrawingSpec.sections[].label`) is caller-supplied and was the one text node in the writer that interpolated it raw: `</text><image href=x onerror=…/><text>` executed in the viewer's session, with the session JWT in `localStorage`. A `<script>` inserted via innerHTML does not run and an `<image onerror>` does — which is why "it's inert SVG" is not a defence. Likewise `supplier_parts._safe_link` keeps `javascript:` and `data:` out of a stored `href`, checked on write *and* on read so a row written before the check is still safe.

**`persistence._rows_by_json_field` interpolates its `field`** — a JSON path is not something a driver will bind — so it is validated against `^[A-Za-z_][A-Za-z0-9_]*$`. Every caller passes a literal and a test asserts they still do; the check is there because the first one that forwards a request field would otherwise be an injection, and `catalog_ref') OR 1=1--` reached the statement without it.

**State & persistence.** The durable source of truth is a **SQLAlchemy datastore** (`app/db.py`): accounts, documents, candidates and assemblies persist as transactional rows via `services/persistence.py` (same function signatures as before — the file-JSON backing was swapped out underneath). Dev/tests use embedded **SQLite** (WAL mode) at `backend/data/forge.db`; set `DATABASE_URL` to a `postgresql+psycopg://…` URL for production (MVCC concurrent writers, pooling, TLS, horizontal scale) — no code change. On startup `main.py` calls `init_db()` + `migrate_json_files()` (one-time lossless import of any legacy `backend/data/*/*.json`). Purely in-memory (rebuilt/lazily re-derived, lost on restart): the optimize job dicts (`_jobs`/`_results`), the evaluated-solid cache `_SOLID_CACHE`, and the `CANDIDATE_DATA`/`ASSEMBLY_DATA` working caches; on startup only candidate/assembly **metadata** is restored and solids are re-evaluated lazily. Tests run against an isolated temp DB (`tests/conftest.py` sets `DATABASE_URL` before app import).

The datastore is one table — `records(kind, id, owner_id, data)` — so a new persisted type is a new `kind` and no migration. That is how `trajectory` was added. Filter inside a row with `persistence._rows_by_json_field`, which is dialect-aware (SQLite `json_extract`, Postgres `->>`); loading every row to test one field means deserializing whole feature trees.

**Geometry is only comparable when the conditions match.** `DerivedCache` records `resolution`, `sampler` (`brep` | `native` | `numpy`) and `mesh_hash`. On the SDF paths `resolution` is a *total voxel budget*, not per-axis, and `capped_resolution` clamps it per plan — so the same document yields different geometry depending on who asks. On the B-rep path it only controls tessellation smoothness: a flat body meshes identically at any resolution, and a curved one converges. Pin it for anything comparing meshes across runs.

**Units in exported files.** The kernel works in metres; STEP is written in **millimetres** with an explicit `SI_UNIT(.MILLI.,.METRE.)` context, by both writers. The faceted one previously emitted raw metre values with no unit context at all and passed an `AXIS2_PLACEMENT_3D` where a representation context belongs, so an 80 mm plate imported as 0.08 mm.

## LLM configuration

Opt-in via `backend/.env`: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` (provider-agnostic OpenAI-style chat protocol; defaults target Moonshot/Kimi, also works with OpenRouter). Text-to-CAD, text-to-assembly and the Copilot loop all require a key — see "Text-to-CAD needs a model, and there is no fallback" above; without one, `create_document(prompt=…)` and `text_to_assembly` raise `TextToCadUnavailable` rather than degrading to a rule-based parser, which no longer exists.

## OAuth sign-in configuration

Optional, opt-in via `backend/.env` (same pattern as billing/LLM — unset means the feature is off and password login is the only path): `OAUTH_GOOGLE_CLIENT_ID`/`OAUTH_GOOGLE_CLIENT_SECRET` and/or `OAUTH_GITHUB_CLIENT_ID`/`OAUTH_GITHUB_CLIENT_SECRET`, plus `PUBLIC_BASE_URL` (register `{PUBLIC_BASE_URL}/api/auth/oauth/{provider}/callback` as the redirect URI in the provider console). The flow (`services/oauth.py`) is Authorization Code + PKCE (S256) with a server-side single-use `state`; token exchange is server-to-server and provider tokens are never stored or sent to the browser — the SPA receives a single-use 60-second handoff code and redeems it at `POST /api/auth/oauth/exchange` for the session JWT. Only verified provider emails are accepted; identities link to accounts by provider subject id first, then verified email (`Account.oauth_ids`).

## Subscription & billing configuration

Accounts/plans/entitlements always run; `services/billing.py` is a pluggable payment provider following the same opt-in pattern. With **no** `STRIPE_API_KEY`, plan changes apply immediately (local self-serve) so dev needs no payment credentials. Set these in `backend/.env` to go live: `STRIPE_API_KEY` (secret key), `STRIPE_WEBHOOK_SECRET` (`whsec_…`, required to accept webhooks), `STRIPE_PRICE_PRO` / `STRIPE_PRICE_ENTERPRISE` (recurring price ids), `PUBLIC_BASE_URL` (post-checkout redirect base). In live mode a paid upgrade returns a Stripe Checkout URL and the plan is granted **only** by the signature-verified webhook at `POST /api/auth/webhook/stripe` — never trusted from the browser redirect. Stripe calls go through `httpx` (no `stripe` SDK). `FORGE_AUTH_REQUIRED=1` flips the whole API from dev-account fallback to enforced auth. Documents are owner-scoped and isolated per account (see `document_service.can_access`).

## gstack skills

This environment has [gstack](https://github.com/garrytan/gstack) installed (Garry Tan's Claude Code setup) — a suite of slash-command "skills" that act as specialist roles across the dev lifecycle. Invoke `/gstack` to route a request, or call a skill directly. Full reference: `~/.claude/skills/gstack/docs/skills.md`.

Lifecycle order: `office-hours → spec → autoplan → implement → review → qa → ship → land-and-deploy → retro`.

**Plan & product**
- `/office-hours` — YC-style reframe; start here on a new idea. `/spec` — turn vague intent into an executable spec.
- `/plan-ceo-review` — find the 10-star product in the request. `/plan-eng-review` — lock architecture/data-flow/tests (the only required review gate). `/plan-design-review` — audit the plan's UX before code. `/plan-devex-review` — DX/time-to-hello-world. `/autoplan` — run CEO→design→eng→DX automatically.

**Design**
- `/design-consultation` — build a design system from scratch (writes `DESIGN.md`). `/design-shotgun` — generate & compare visual variants. `/design-html` — mockup → production HTML. `/design-review` — live-site visual audit + fix loop.

**Build, review, QA**
- `/review` — production-bug hunt (auto-fixes obvious ones). `/investigate` — root-cause debugging (no fix without investigation). `/codex` — independent second opinion from OpenAI Codex. `/qa` / `/qa-only` — browser-driven testing (diff-aware). `/browse` — real Chromium eyes for the agent. `/health` — type/lint/test/dead-code dashboard.

**Ship & operate**
- `/ship` — sync, test, coverage audit, push, open PR. `/land-and-deploy` — merge → deploy → verify prod (`/setup-deploy` first). `/canary` — post-deploy monitoring. `/benchmark` — perf baselines. `/cso` — OWASP+STRIDE security audit. `/document-release` / `/document-generate` — keep docs in sync / generate Diataxis docs. `/retro` — team-aware retrospective.

**Safety & utility**
- `/careful` (warn on destructive commands), `/freeze` (lock edits to one dir), `/guard` (both), `/unfreeze`. `/make-pdf`, `/diagram`, `/learn` (session memory), `/context-save` + `/context-restore`, `/gstack-upgrade`.

Note: gstack stores its own per-project state under `~/.gstack/projects/`, separate from this repo.
